# Platform Landscape: Open Personal Memory Layer / Personal AI Platform

**Date compiled:** September 2026 (desk research session; source dates as cited inline)
**Prepared for:** Orivory (MIT-licensed, self-hosted AI second brain — FastAPI + Next.js, LangGraph corrective RAG, hybrid retrieval + reranking, salience/decay memory store, knowledge graph, proactive digest, connectors, team workspaces)
**Method:** 20 distinct web searches and page fetches via Exa (search + fetch). Every factual claim carries an inline source URL. GitHub star counts, license fields, and launch/sunset dates are as reported by the cited pages at retrieval time and change quickly — re-verify before quoting externally. Nothing in this document is inferred beyond what sources state; where a gap is claimed ("nobody ships X"), the evidence for the negative is listed explicitly.

## 1. Mem0's OpenMemory — the closest prior art, and it is being sunset

**What it is.** OpenMemory MCP launched 13 May 2025 as "a private, local-first memory server that creates a shared, persistent memory layer for your MCP-compatible tools," running entirely on your machine with a built-in dashboard. It exposed four MCP tools — `add_memories`, `search_memory`, `list_memories`, `delete_all_memories` — over per-client SSE endpoints, so context stored via Cursor could be recalled in Claude Desktop or Windsurf. ([launch blog](https://mem0.ai/blog/introducing-openmemory-mcp))

**Architecture.** Dockerized FastAPI + Postgres (relational metadata) + Qdrant (vector store), with a Next.js dashboard on localhost:3000 and MCP server on :8765. Memory content stays local; the only external call by default is to the configured LLM/embedding provider (OpenAI), swappable for Ollama for fully-local operation. ([architecture deep-dive](https://mem0.ai/blog/how-to-make-your-clients-more-context-aware-with-openmemory-mcp), [third-party walkthrough](https://dreaming.press/posts/how-to-run-local-memory-server-openmemory-mcp.html), [README](https://github.com/mem0ai/mem0/blob/main/openmemory/README.md))

**Governance features it did ship (important — this is the closest anyone came).** The architecture post claims you can "pause or revoke any client's access at the app or memory level, with audit logs for every read or write," with per-app ACLs and state transitions (active/paused/archived). The consumer-facing landing page claims permission-based access ("LLM tools like Cursor can read or create memories only when you allow them to. You can see what they accessed") and GDPR-readiness marketing. ([architecture blog](https://mem0.ai/blog/how-to-make-your-clients-more-context-aware-with-openmemory-mcp), [openmemory landing](https://mem0.ai/openmemory-mcp-3))

**The headline finding: OpenMemory is being sunset.** The current README in `mem0ai/mem0` carries a sunsetting notice: "OpenMemory is being sunset. For local self-hosted memory with a dashboard, please use the Mem0 self-hosted server instead." The successor is a developer-facing self-hosted server (`cd server && make bootstrap`, auth + API keys + dashboard) that positions itself as infrastructure for teams, not a personal memory hub for end users. ([README with sunsetting notice](https://github.com/mem0ai/mem0/blob/main/openmemory/README.md), [mem0 repo](https://github.com/mem0ai/mem0) — Apache 2.0, ~61–65K stars)

**What OpenMemory did NOT do (gap map):**
- **No knowledge graph** — vector-only retrieval via Qdrant; no entities, relations, clusters, or temporal logic. ([architecture blog](https://mem0.ai/blog/how-to-make-your-clients-more-context-aware-with-openmemory-mcp))
- **No ingestion connectors** — no web clipper, RSS, Notion, Gmail, or Drive; memory enters only via MCP clients' chat text.
- **No proactive surfacing** — nothing schedules digests or pushes recall; purely pull-based `search_memory`.
- **No salience/decay/curation model** — flat memory list with add/edit/delete; the third-party walkthrough describes "browsing, searching, and deleting memories by hand." ([walkthrough](https://dreaming.press/posts/how-to-run-local-memory-server-openmemory-mcp.html))
- **No memory portability/export** — a PAM-compatible interchange spec explicitly notes "OpenMemory... storage is vector-based... not human-readable files," and no export format exists. ([PLUR MCP memory survey](https://plur.ai/blog/mcp-server-ai-agent-memory/))
- **No cross-device sync, no team workspaces, no end-user "life" scope** — it is scoped to a single workstation and oriented at coding-agent workflows (Cursor/Claude/Windsurf/Cline).
- **Audit/permission claims were early and shallow** — per-client SSE URLs functioned as bearer identity; the deeper audit feature appears in marketing/blog claims rather than a documented per-agent permission model, and the project is now deprecated anyway.

**Strategic read:** The single closest prior art to "a memory hub for all agents" was built, gained attention, and was withdrawn in favor of a dev-infrastructure play. The niche it validated (local MCP memory hub + dashboard + access control) is now vacant by its owner's own choice. ([README sunsetting notice](https://github.com/mem0ai/mem0/blob/main/openmemory/README.md))

## 3. MCP memory ecosystem and portability standards

**How many memory servers exist.** The mcp.so directory alone lists **611 servers/clients in its "Memory & Knowledge" category** ([mcp.so](https://mcp.so/categories/memory-knowledge)). Across the whole MCP ecosystem, careful censuses put the total at **~9,600 distinct servers (official registry dedupe) up to ~17,500 including forks/directories** ([AlatiRok census](https://alatirok.com/mcp-server-statistics-2026/)). Memory is one of the most-starred categories: in one directory's ranking, "Memory (Knowledge Graph)" (~74K★) and "OpenMemory MCP" (~59.9K★) and "Graphiti MCP" (~28.2K★) sit in the top 10 of all 520 tracked servers ([MCP Trove report](https://mcptrove.com/report)). The ecosystem is large, chaotic, and quality-unverified: of ~80K listed servers, only ~12K were verified alive in one audit ([Unfragile MCP Census](https://unfragile.ai/report/mcp-census-2026)).

**What they look like.** The official reference `@modelcontextprotocol/server-memory` is a local knowledge-graph store (entities/observations/relations). Third parties include Mem0's OpenMemory, Zep's MCP server, PLUR (YAML "engrams" with confidence/provenance), pg-mnemosyne (Postgres multi-agent hub), Cognee, and dozens of community entries. ([PLUR survey](https://plur.ai/blog/mcp-server-ai-agent-memory/))

**Critical structural fact: MCP standardizes transport, not memory.** "What MCP does not define is the memory format... two MCP memory servers can be fully protocol-compatible and store memory in completely different ways." ([PLUR survey](https://plur.ai/blog/mcp-server-ai-agent-memory/)) Also notable for anyone building per-agent permissions: one project documents that "MCP protocol doesn't pass tool identity" and that per-caller audit is "blocked by MCP spec" — caller identity must be reconstructed at the hub layer (e.g., per-client endpoint tokens). ([piia-engram limitations table](https://github.com/caioribeiroclw-pixel/piia-engram))

**Is there an emerging memory-portability standard? Many — and that is the finding.** At least **six** independently authored proposals exist, none backed by a major platform:

1. **UMP — Universal Memory Protocol**: "one record format + six operations," MCP/HTTP/file bindings, portable signed file; "a protocol, not a product." ([repo](https://github.com/edihasaj/universal-memory-protocol))
2. **AIMEM Bundle — IETF Internet-Draft**: vendor-neutral JSON memory bundle with export/import HTTP profile, explicitly aimed at GDPR right-to-erasure interoperability. ([draft-vu-aimem-bundle-00](https://www.ietf.org/archive/id/draft-vu-aimem-bundle-00.html))
3. **OMS — Open Memory Specification**: binary content-addressed "memory grain" (`.mg`) containers, CAL query language, SML LLM-context markup, GDPR/CCPA primitives, DID signing. ([repo](https://github.com/openmemoryspec/oms))
4. **OAMP — Open Agent Memory Protocol**: JSON interchange with mandatory encryption-at-rest, full export, real (non-soft) deletion "GDPR Article 17 compliant," provenance. ([repo](https://github.com/deep-thinking-lab/open-agent-memory-protocol))
5. **PAM — Portable AI Memory**: vCard-for-memory interchange format with provider import mappings for ChatGPT/Claude/Gemini/Copilot/Grok exports; states plainly that "AI providers do not natively support PAM." ([spec](https://github.com/portable-ai-memory/portable-ai-memory/blob/master/spec.md))
6. **MIF — Memory Interchange Format (SEP-002)**: JSON/YAML/JSONL export with consent-aware sharing and auditability. ([spec](https://github.com/varun29ankuS/shodh-memory/blob/main/seps/SEP-002-memory-interchange-format.md))

Plus an academic entry: **Portable Agent Memory** (arXiv) with Merkle-DAG provenance, capability-scoped access tokens, and injection-resistant re-hydration, which observes that "MCP standardizes tool access and A2A standardizes task delegation, [but] no prior protocol provides verified memory portability" and that Mem0's cloud creates "a new form of vendor lock-in." ([arXiv:2605.11032](https://arxiv.org/html/2605.11032v1))

**Who is trying to standardize:** as of this research, only individual developers and small teams — no MCP core-spec workgroup, no OpenAI/Anthropic/Google endorsement appears in any of the above sources, and the PAM spec concedes providers "do not natively support" any such format. The standardization layer is a fragmented open field.

## 4. Personal data ownership prior art — and its lessons

**Solid (Tim Berners-Lee pods).** Solid gives each person a "pod" — a personal online data store with fine-grained access control that apps request rather than assume. ([solidproject.org](https://solidproject.org/), [Fast Company profile](https://www.fastcompany.com/91231379/tim-berners-lee-solid-inrupt-pod-digital-wallet)) Stewardship passed from Inrupt to the **Open Data Institute in October 2024**; a W3C Linked Web Storage Working Group is standardizing it, and Berners-Lee explicitly ties Solid's renewed relevance to GenAI: "it fits well as the data storage layer for personal Agentic AI." ([EDM Council webinar Q&A](https://edmcouncil.org/announcement/blog-one-copy-of-the-truth-sir-tim-berners-lee-on-solid-and-the-future-of-enterprise-data/)) **The honest status:** Berners-Lee himself writes (2024) that "no one is running a public pod platform equivalent to Dropbox... solidcommunity.net is for research and experimentation, not personal data," that community Solid apps carry "technical debt," and — in the webinar — concedes "Solid has struggled with adoption for 10 years now." A questioner in that same Q&A reports losing their pod in 2020 when the free experimental host shut down. ([Design Issues vision essay](https://www.w3.org/DesignIssues/Vision.html), [Q&A PDF](https://edmcouncil.org/wp-content/uploads/2026/08/EDMWebinar_Solid-and-ODI_Q-and-A_20260714.pdf)) **Lessons that transfer:** (1) protocol-first, app-second stalls — users arrive for working apps, not pods; (2) free experimental hosts that vanish destroy trust — durability guarantees are a product feature; (3) the AI-agent angle is the first adoption story with real pull in a decade.

**Local-first software (Ink & Switch).** The 2019 essay defines seven ideals (no spinners, multi-device, offline, longevity, privacy by default, user ownership, speed) and proposes CRDTs as the foundation, while delivering a verdict Orivory should internalize: "self-hosting is not a viable option for the vast majority of users who do not want to become system administrators." ([Ink & Switch essay](https://www.inkandswitch.com/essay/local-first/)) The 2025 "malleable software" essay extends this: AI code generation alone doesn't create user agency — tools must compose over shared, locally-owned data. ([Malleable software](https://www.inkandswitch.com/essay/malleable-software/)) **Transferable lessons:** ownership must not cost the cloud app's conveniences (sync, collaboration); a memory hub needs an effortless hosted option or dead-simple installer, and its data should be inspectable plain formats.

**"Personal AI OS" projects.**
- **Second Me (Mindverse)** — Apache 2.0, ~15.7K★, created March 2025; locally trained "AI self" using Hierarchical Memory Modeling, with an optional P2P network where "anyone or any app can connect with your permission." ([repo](https://github.com/mindverse/Second-Me)) But third-party tracking shows the momentum evaporated: a commit-and-release output index of **0/100**, last release v1.0.1 in May 2025, "coasting a little on attention." ([Repository Radar](https://repositoryradar.dev/repo/mindverse/second-me)) Lesson: virality without a maintained daily-use product decays fast.
- **Open Interpreter / 01** — the voice-hardware platform is AGPL, ~5.1K★, and still carries the warning "this experimental project is under rapid development and lacks basic safeguards... only run this on devices without sensitive information"; it never reached a 1.0. ([01 repo](https://github.com/OpenInterpreter/01)) The main Open Interpreter project has since pivoted into a Codex-fork coding agent. ([openinterpreter repo](https://github.com/openinterpreter/openinterpreter/)) Lesson: raw code-execution power without safety/permission layers doesn't hold a consumer surface.
- **OpenClaw** — the counter-example and the earthquake: a self-hosted personal agent (local Gateway + messaging channels + proactive cron jobs + persistent Markdown memory), created Nov 2025, which became **the most-starred software repo on GitHub in under five months (~346–388K stars)**, now stewarded by a non-profit OpenClaw Foundation with the whole product **MIT-licensed**. ([openclaw.ai](https://openclaw.ai/), [GitHub repo](https://github.com/openclaw/openclaw), [Why OpenClaw](https://docs.openclaw.ai/start/why-openclaw)) Its memory, however, is agent-runtime state (local Markdown, skills, plugins) — not a curated, governed personal knowledge store; and its own docs admit "sandboxing and exec approvals are off by default." ([Why OpenClaw](https://docs.openclaw.ai/start/why-openclaw)) **Lesson:** the demand for a self-hosted personal AI with memory is now proven at record scale — but the *memory layer* of that wave is primitive, which is precisely an opportunity for a dedicated hub that OpenClaw-class agents can read/write through MCP.

## 5. Memory governance / permissions / audit — the emptiest part of the map

**What exists today (closest prior art, all small or partial):**
- **OpenMemory (sunset)** — per-client app-level access control + claimed read/write audit logs; the most consumer-legible version ever shipped, now deprecated. ([architecture blog](https://mem0.ai/blog/how-to-make-your-clients-more-context-aware-with-openmemory-mcp))
- **piia-engram** — a local-first personal identity layer for coding agents with caller trust levels, an on-by-default local audit log, a "Memory Lens" preview showing "exactly what any AI caller would receive, and what governance withheld," and a hash-chained disclosure ledger. Honest about limits: "Per-caller audit (blocked by MCP spec)" and "MCP protocol doesn't pass tool identity." ([repo](https://github.com/caioribeiroclw-pixel/piia-engram))
- **ai-memory-mcp** — deny-first permission rules with namespace/op/agent patterns and ask-user escalation for memory writes/consolidation. ([admin guide](https://github.com/alphaonedev/ai-memory-mcp/blob/main/docs/ADMIN_GUIDE.md))
- **ShieldCortex** — MIT-licensed memory-security layer: injection scanning of memory writes, audit export (JSON/CSV), staleness/decay scoring, replay and review surfaces. ([product page](https://drakonsystems.com/products/shieldcortex))
- **velesdb-memory** — local memory engine whose `why()` tool returns the auditable trail of which memories produced an answer, explicitly marketing EU AI Act traceability. ([crate docs](https://docs.rs/crate/velesdb-memory/0.11.0))
- **Dust (enterprise SaaS)** — dual-layer permission model separating "what agents can access" from "who can use them," with 365-day audit logs — but for company workspaces, not personal memory. ([dust.tt](https://dust.tt/home/product))
- **sonz.ai (commercial agent platform)** — disclosure audit logging every "disclosed/redacted" memory decision, k-anonymized cross-user "wisdom" layer. ([docs](https://sonz.ai/docs/en/shared-memory))
- **ChatGPT / Claude** — user-visible memory editing, but no per-third-party-agent permissions, no "which AI saw what" ledger, and deletion is fragmented (OpenAI: "to fully delete something ChatGPT may know about you, you'll need to delete every source"). ([OpenAI FAQ](https://help.openai.com/articles/8590148-memory-faq))

**What nobody ships:** an end-user-facing, self-hosted **personal** memory hub with per-agent permissions, a "which AI saw what" access ledger, and right-to-be-forgotten tooling across arbitrary agents. The negative evidence: (a) the closest OSS projects above are single-developer-scale and coding-agent-scoped; (b) consumer platforms (ChatGPT/Claude) govern only their own memory; (c) the standards drafts (AIMEM, OAMP, OMS, PAM) all specify *formats* for consent/erasure/provenance but none ships as a working product with a UI. ([PAM spec](https://github.com/portable-ai-memory/portable-ai-memory/blob/master/spec.md), [AIMEM draft](https://www.ietf.org/archive/id/draft-vu-aimem-bundle-00.html))

**Regulatory tailwind is real and documented.** GDPR Article 17 (right to erasure) is formally strained by LLM memory: personal data absorbed into model parameters is practically unerased, and regulators focus on output-level compliance. ([FirmAdapt analysis](https://firmadapt.com/blog/gdpr-right-forgotten-generative-ai-article-17), [Springer AI & Ethics paper](https://link.springer.com/article/10.1007/s43681-024-00573-9)) The EDPB's latest guidance "confirms that individuals can request deletion and other rights whenever AI models include personal data." ([Leiden Law Blog](https://www.leidenlawblog.nl/articles/erasing-personal-data-in-an-ai-era)) Compliance practitioners now advise organizations to audit ChatGPT memory before rollouts and build "processes for handling data subject deletion requests relating to AI memory." ([AI Policy Desk](https://www.aipolicydesk.com/blog/chatgpt-memory-dreaming-v3-privacy-governance-2026)) Critically, the same analyses identify **RAG/retrievable storage as "architecturally the cleanest solution" for erasure** — exactly the architecture a self-hosted memory hub has. ([FirmAdapt](https://firmadapt.com/blog/gdpr-right-forgotten-generative-ai-article-17)) The EU AI Act adds transparency duties for GPAI providers (technical documentation, training-data summaries) ([Article 53](https://ai-act-service-desk.ec.europa.eu/en/ai-act/article-53)), and even a small OSS memory engine now cites AI Act enforceability as a selling point. ([velesdb docs](https://docs.rs/crate/velesdb-memory/0.11.0))

## 6. Proactive agent platforms — crowded for tasks, empty for governed personal memory

- **Khoj** — the reference OSS "AI second brain": self-hostable, indexes docs (Obsidian, PDFs, org-mode), custom agents, and **cron-style Automations** that email newsletters/digests ("summary of top 5 posts from Hacker News... every morning at 8:00 AM"). ([GitHub](https://github.com/khoj-ai/khoj), [i-scoop deep dive](https://www.i-scoop.eu/khoj/), [2026 review](https://aifoss.dev/blog/khoj-review-2026/)) Reviewers note a persistent gap: "The hosted version at app.khoj.dev consistently gets features before the self-hosted Docker release." Khoj automations run over *indexed documents* — there is no governed memory store, no KG, no per-agent access control beneath the digest.
- **Lindy** — hosted-only business-agent platform (inbox/meetings/CRM), per-task pricing; "Lindy is hosted-only. Self-host is one of n8n's core differentiators." ([Lindy vs n8n comparison](https://buildersos.ai/compare/lindy-vs-n8n/))
- **n8n** — AGPL-licensed, self-host-first visual workflow runtime with AI-agent nodes; the strongest OSS automation substrate, but memory and agent logic are DIY wiring. ([same comparison](https://buildersos.ai/compare/lindy-vs-n8n/), [Lindy's own comparison](https://www.lindy.ai/blog/n8n-ai-agents))
- **Dust** — enterprise "multiplayer AI": 70+ connectors, Pods, governed permissions + audit logs — company-scoped, closed, not personal. ([dust.tt](https://dust.tt/home/product))
- **OpenClaw-class self-hosted agents** — genuinely proactive ("Proactive AF: cron jobs, reminders, background tasks") and self-hosted, but memory is local Markdown runtime state, not a curated knowledge store. ([openclaw.ai quotes](https://openclaw.ai/), [docs](https://docs.openclaw.ai/start/why-openclaw))
- A 2026 landscape survey buckets the whole field into self-hosted personal agents (OpenClaw, Hermes, Agent Zero, Khoj, AutoGPT, Open Interpreter), managed work agents (ChatGPT Agent, Claude Cowork, Lindy, Manus, Genspark, Dust), and memory-first assistants (TwinMind). ([Thorsten Meyer AI survey](https://thorstenmeyerai.com/reality-check/the-new-personal-agent-layer/))

**What's missing:** every scheduled-agent product runs over either indexed documents (Khoj) or SaaS connectors (Lindy/Dust/n8n). **No OSS product schedules agent runs over a personal memory store with permission-aware, provenance-tracked retrieval** — i.e., a morning digest that can cite *why* it may surface each memory, honoring what each connecting agent is allowed to see. The pieces (Khoj's scheduler + a governed hub like Orivory) have not been combined by anyone in this survey.

## 7. Quantified-self / lifelogging capture — commercially consolidated, OSS-orphaned

**The commercial collapse.** On 5 December 2025, Meta acquired Limitless (fka Rewind). Consequences, per the company and press: no new Pendant sales; support for existing customers "at least another year"; subscriptions dropped; **the Rewind desktop app sunsets with all screen and audio capture disabled from 19 December 2025**; and service is withdrawn entirely from the EU, UK, Brazil, China, Israel, South Korea, and Turkey, with local data permanently deleted after a download window. ([Limitless announcement](https://www.limitless.ai/), [Reuters](https://www.reuters.com/business/meta-acquires-ai-wearables-startup-limitless-2025-12-05/), [TechCrunch](https://techcrunch.com/2025/12/05/meta-acquires-ai-device-startup-limitless/), [9to5Mac](https://9to5mac.com/2025/12/05/rewind-limitless-meta-acquisition/)) TechCrunch reports the company "hinted that the increased competition... made it difficult to compete" against Meta and OpenAI hardware. **Net effect:** continuous personal capture — the most data-rich input a second brain can have — is now either inside Meta's walled garden or gone in major markets.

**The OSS state of capture.** Screenshot-based lifelogging survives in **OpenRecall** (fully open-source, local OCR + semantic search, cross-platform; positions itself against Windows Recall and Rewind). ([openrecall repo](https://github.com/openrecall/openrecall)) Voice capture has a healthy but *fragmented* OSS tail, all whisper.cpp-class and local-first, none connected to a shared memory hub: OpenWhispr (dictation + notes + MCP server), LocalVoice (offline dictation), VoiceFlow (dictation + meeting recorder with BYO-LLM summaries), Amical (context-aware dictation), VoiceVault (record → transcribe → auto-summarize → RAG search → Obsidian export). ([OpenWhispr](https://github.com/OpenWhispr/openwhispr), [LocalVoice](https://github.com/iptoux/localvoice), [VoiceFlow](https://github.com/infiniV/VoiceFlow), [VoiceVault](https://github.com/PJH720/VoiceVault)) Note these are transcription utilities, not the commercial polish of AudioPen/VoicePal — this survey found no OSS category-killer there, and none of them writes into a governed long-term memory store (VoiceVault's Obsidian markdown export is the nearest gesture).

**Read:** "capture everything into one brain" is **open in OSS** — the commercial leader exited to Meta, the OSS alternatives are single-purpose utilities, and the integration point (one hub that ingests clips, voice, RSS, screens into one salience-weighted, decay-aware memory) is unclaimed.

## WHITE SPACE — gaps nobody fills (with the negative evidence)

1. **The "local MCP memory hub + dashboard + access control" category is vacant by its founder's choice.** Mem0 sunset OpenMemory and redirected self-hosters to a developer server. Evidence: the sunsetting notice in the official README ([link](https://github.com/mem0ai/mem0/blob/main/openmemory/README.md)). Nothing else in the MCP memory tier pairs a user-facing dashboard with access control — the official reference server has no UI ([PLUR survey](https://plur.ai/blog/mcp-server-ai-agent-memory/)), and the directory shows no successor product ([mcp.so](https://mcp.so/categories/memory-knowledge)).

2. **Per-agent permissions on personal memory + "which AI saw what" ledger.** No end-user product ships this. Closest: OpenMemory's sunset ACLs; piia-engram's trust levels + disclosure ledger (single-developer, coding-agent scoped, and it documents that MCP doesn't pass caller identity — a problem a hub can solve with per-client endpoint tokens, as OpenMemory's per-client SSE URLs sketched). ([piia-engram](https://github.com/caioribeiroclw-pixel/piia-engram), [OpenMemory architecture](https://mem0.ai/blog/how-to-make-your-clients-more-context-aware-with-openmemory-mcp)) Consumer platforms don't offer it at all: OpenAI's deletion FAQ shows even *user-side* deletion is source-by-source ([FAQ](https://help.openai.com/articles/8590148-memory-faq)).

3. **Right-to-be-forgotten as a product feature.** GDPR Art. 17 and EDPB guidance make erasure a live obligation for AI memory ([Leiden](https://www.leidenlawblog.nl/articles/erasing-personal-data-in-an-ai-era), [FirmAdapt](https://firmadapt.com/blog/gdpr-right-forgotten-generative-ai-article-17)), and the clean architectural answer — retrievable storage with provenance — is exactly what a memory hub is. Yet no surveyed hub ships erasure receipts, provenance-cascading deletion, or export-for-compliance. Standards drafts specify these on paper only ([OAMP](https://github.com/deep-thinking-lab/open-agent-memory-protocol), [AIMEM](https://www.ietf.org/archive/id/draft-vu-aimem-bundle-00.html)).

4. **Memory portability is six competing specs with zero platform adoption.** UMP, AIMEM, OMS, OAMP, PAM, MIF all exist; PAM itself concedes "AI providers do not natively support PAM" ([spec](https://github.com/portable-ai-memory/portable-ai-memory/blob/master/spec.md)). A hub that *actually imports* ChatGPT/Claude/Gemini exports and re-serves them via MCP would be the first working implementation of what all six specs merely describe (PAM even documents the export file formats, [spec §20/25](https://github.com/portable-ai-memory/portable-ai-memory/blob/master/spec.md)).

5. **Proactive surfacing from a governed personal memory store.** Khoj schedules over documents; Lindy/Dust schedule over SaaS; OpenClaw schedules over its own runtime state. Nobody schedules digests over permission-aware, provenance-tracked personal memory. Evidence: feature sets cited in section 6.

6. **The OpenClaw wave has no memory home.** ~346–388K stars validated self-hosted personal agents ([openclaw.ai](https://openclaw.ai/)), but their memory is local Markdown state with no curation UI, no graph, no governance ([Why OpenClaw](https://docs.openclaw.ai/start/why-openclaw), [DigitalOcean explainer](https://www.digitalocean.com/resources/articles/what-is-openclaw)). A standalone, MIT/Apache memory hub that OpenClaw/Hermes/any-MCP-agent can read and write — with the user in control — is complementary, not competitive, to the biggest OSS wave in the space.

7. **Salience/decay + consolidation is academically validated, commercially absent.** Memoripy (decay + reinforcement + spreading activation) exists as a research-grade library ([PyPI](https://pypi.org/project/memoripy/)); Letta's sleep-time compute validates offline consolidation ([paper](https://arxiv.org/abs/2504.13171)); ChatGPT's own team abandoned manual memory management because it "became stale" ([FAQ](https://help.openai.com/articles/8590148-memory-faq)). No self-hosted hub ships salience-weighted, decaying, consolidating memory with user-visible controls over the policy.

8. **Capture is orphaned.** Limitless→Meta killed the leading commercial lifelog and exited the EU/UK entirely ([Limitless](https://www.limitless.ai/), [TechCrunch](https://techcrunch.com/2025/12/05/meta-acquires-ai-device-startup-limitless/)); OSS capture is fragmented single-purpose tools ([OpenRecall](https://github.com/openrecall/openrecall), [OpenWhispr](https://github.com/OpenWhispr/openwhispr)). "One hub that capture tools feed into" has no incumbent.

9. **Graph + governance + UX co-exist nowhere.** The strongest KG (Graphiti) has no end-user app and deprecated its community self-host ([FAQ](https://help.getzep.com/faq.mdx)); the products with governance UX (Dust) are enterprise SaaS ([dust.tt](https://dust.tt/home/product)); the OSS hubs with UIs (OpenMemory, memU) have no KG. Each leg of Orivory's architecture exists alone; the intersection is unoccupied.

## Key takeaways

- **The closest prior art just left the field:** Mem0's OpenMemory — local MCP memory server, dashboard, per-app ACLs, audit logs — carries an official sunsetting notice; its successor is team dev-infrastructure, not a personal hub. ([README](https://github.com/mem0ai/mem0/blob/main/openmemory/README.md))
- **The memory-hub market splits into three archetypes and they never overlap:** dev SDKs with no user surface (Letta, Cognee, LangMem, Graphiti), walled-garden consumer memory (ChatGPT, Claude), and narrow local dev-memory (OpenMemory†, memU). No OSS project combines life-scope ingestion + curation UI + KG + proactive + governance.
- **Governance is the emptiest quadrant and has regulatory tailwind:** GDPR Art. 17/EDPB guidance and EU AI Act transparency duties all push toward retrievable, auditable, erasable memory — and analysts name RAG-style retrievable storage as the architecturally clean erasure path, i.e., exactly a memory hub. ([Leiden](https://www.leidenlawblog.nl/articles/erasing-personal-data-in-an-ai-era), [FirmAdapt](https://firmadapt.com/blog/gdpr-right-forgotten-generative-ai-article-17))
- **The MCP layer has a structural hole Orivory can own:** MCP doesn't define a memory format and doesn't pass caller identity, so per-agent permissions must be built at the hub (per-client tokens/endpoint identity). piia-engram documents this limitation; OpenMemory's per-client SSE URLs were the only serious attempt. ([piia-engram](https://github.com/caioribeiroclw-pixel/piia-engram), [PLUR survey](https://plur.ai/blog/mcp-server-ai-agent-memory/))
- **Memory portability: six specs, zero adoption** — an implementation, not another spec, is the white space; PAM already documents the ChatGPT/Claude/Gemini export mappings a hub could import. ([PAM](https://github.com/portable-ai-memory/portable-ai-memory/blob/master/spec.md))
- **Ride the OpenClaw wave, don't fight it:** the biggest OSS personal-agent project in history (~346–388K★, MIT, non-profit foundation) ships primitive Markdown memory; an MCP-native governed memory hub is its missing subsystem. ([openclaw.ai](https://openclaw.ai/), [docs](https://docs.openclaw.ai/start/why-openclaw))
- **Proactive digest over governed memory is unclaimed:** Khoj schedules over documents, Lindy/Dust over SaaS; no one schedules over permission-aware personal memory with provenance. ([Khoj](https://github.com/khoj-ai/khoj), [comparison](https://buildersos.ai/compare/lindy-vs-n8n/))
- **Lifelogging consolidated into Meta and exited Europe** — OSS capture (OpenRecall, OpenWhispr, VoiceVault et al.) is fragmented and hub-less, making "capture everything into one brain" an open OSS position. ([Limitless](https://www.limitless.ai/), [9to5Mac](https://9to5mac.com/2025/12/05/rewind-limitless-meta-acquisition/))
- **Data-ownership history says: apps first, protocol second, durability always.** Solid's 10-year adoption struggle, vanishing free pod hosts, Second Me's stalled momentum, and Ink & Switch's "self-hosting is not viable for most users" verdict all point to: ship a working daily-use app with dead-simple install, keep data in inspectable formats, and treat persistence guarantees as a feature. ([Solid Q&A](https://edmcouncil.org/wp-content/uploads/2026/08/EDMWebinar_Solid-and-ODI_Q-and-A_20260714.pdf), [Ink & Switch](https://www.inkandswitch.com/essay/local-first/), [Second Me tracking](https://repositoryradar.dev/repo/mindverse/second-me))
- **Positioning synthesis for Orivory:** "the user-owned memory hub that any agent can read, with receipts" — MCP-first (OpenClaw/Claude/Cursor compatibility out of the box), per-agent permissions + access ledger (nothing ships it), erasure receipts (GDPR/AI Act-aligned), platform-export import (PAM mappings), proactive digest over governed memory (nobody does it), and a KG + salience/decay core that the sunset of OpenMemory left unowned.
